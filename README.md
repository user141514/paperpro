# PaperPro · 智能简历诊断与增强工作台

PaperPro 现有两条独立但共用解析与设置基础设施的流程：**求职者端五维诊断**（默认入口）和**经典简历编辑**（保留原功能）。上传数据默认本机处理；从不自动改写用户上传的原始文件。

## 快速使用

当前 Windows 电脑已安装依赖并完成前端构建，网页服务监听：

**http://127.0.0.1:8766/**

双击项目根目录的 **start-paperpro.cmd** 可在服务未启动时启动服务（需保持命令行窗口开启）。默认仅绑定 127.0.0.1，不能被其他设备直接访问。

如果要从零安装，在本目录执行：

    uv sync --python 3.12 --group dev
    cd frontend
    npm ci
    npm run build
    cd ..
    uv run --python 3.12 python -m uvicorn app.main:app --host 127.0.0.1 --port 8766

不得使用 Anaconda/Miniconda；Python 由 uv 管理。前端采用 React + Vite + Mantine + Tabler Icons，后端 FastAPI + RapidOCR + PyMuPDF + python-docx。Microsoft Word 负责高保真 DOCX→PDF 和旧版 DOC 读取；当 Word 不可用时有基础 PDF 备用引擎，极罕见非 BMP 字符会明确拒绝错误导出。

## 求职者端 · 五步诊断（默认首页）

地址：**http://127.0.0.1:8766/**。按 ① 明确数据用途后上传 PDF/DOCX/DOC/PNG/JPG（单文件 10 MB）或粘贴文本 → ② 对照原文校对字段并确认 → ③ 填写必需的目标职位、核对岗位要求及权重（合计 100%），公司与 JD 可选 → ④ 查看五个独立诊断模块的结果、证据与范围 → ⑤ 填写实际修改、采纳为待办，真实完成后单独标记完成，导出清单或诊断报告（TXT/PDF）。

**2026-10-30 V3 闭环：** 对照《功能设计说明书 V3.0》和《功能流程图 V2.0》增加原件与草稿版本、自动保存和刷新续作、冲突核对、单模块重试、只读历史和恢复为新版本。采纳不等于完成；复制示例不会改变待办状态。建议只来自成功模块，不为达到固定条数而补空泛建议，示例仅用于局部修改。目标、字段、要求或模块范围变化会使旧结果需要重新确认；历史报告仍可明确按原版本导出。具体需求、反例与验收边界见 [V3 对照验收](docs/V3_CHECKLIST_ACCEPTANCE_20261030.md)。

**2026-10-20 新增诊断→成稿交接：** 第五步现在可明确点击「继续编辑并导出岗位简历」，将已校对的公司/职位/年月、目标岗位/JD 和勾选建议一次性交给原有 `/classic` 编辑器。只用当前标签页的短时 `sessionStorage`，读取后立即清除；不传递密钥、AI 授权或导出确认，不自动采纳建议，不保存到服务器。经典编辑器显示已选择的改进清单，同时仍必须由用户检查预览并勾选事实审核才能导出。如果原始工作经历标题与由已核对字段重建的标题不同，编辑器会在对应条目内并列显示二者；原始标题只作核对参考，不会自动写入导出文件。删除工作经历时，后续对照记录随之重排。证书和自我评价仅按完整相同的字段去重，避免简介出现相同关键词时误删事实。再次更换文档不会继承旧建议。本次发布只包含简历识别、矛盾核查、岗位诊断、强化建议和人工审核导出能力，不增加额外的职业证据库。

五大结果分别是岗位匹配证据覆盖度（0–1 系数与已确认的能力项权重）、工作经验时间线（相关任职去重月份与空档）、学习潜力证据信号、岗位针对性和有位置的核查疑点。优化建议区分有依据的「需要修正」和「可选深化」；没有可靠日期或潜力证据时显示未知或证据不足，不能用零个月、虚构证据或凑数建议代替。默认纯本地确定性规则；DeepSeek 辅助解读只有本次明确同意后才会外发，且**只能选择规则表中的解释模板与已存在的证据路径**。自然语言由本地模板生成，不能覆盖算法算出的时间、得分或自行编写公司/学历事实。

**描述矛盾核查（试运行）：** 五维诊断中的「简历智能验真」现在能够对同一技术的明确肯定/否定描述进行双原文定位，并生成核查问题和可选修正建议；例如「熟悉 Python」与「Python：不会」。检测区分技能掌握与实际使用、当前能力与过去学习阶段，不会把 JD 要求或资料缺失视作事实矛盾。**只覆盖规则词表与明确措辞，未经真实简历精确率标定，也不会自动改写或替用户裁定哪一句为真。**详细范围、反例与测试见 [描述矛盾核查](docs/RESUME_DESCRIPTION_CONTRADICTIONS.md)。

**解析质量工程验收**：新增 20 份合成 DOCX/PDF（260/260 字段正确）与 4 张清晰合成 PNG/JPEG（49/52 字段正确，94.23%）的本地基准，以及 Android/iPhone 浏览器模拟、Chrome 实际扫描上传→OCR→诊断链路。运行：`uv run --python 3.12 python -m scripts.benchmark_resume_parsing --include-ocr`。这**不是实际简历或手机真机准确率**；具体失败项及边界见 `docs/SYNTHETIC_PARSER_QA.md`。

**甲方工程演示验收**：运行 `uv run --python 3.12 python -m scripts.client_acceptance_smoke`，逐项执行并打印 R7–R10 功能合同的可操作断言与未验证的数据门槛。公开资料与评测说明在 `docs/CLIENT_ACCEPTANCE_OPEN_REFERENCE.md`。另可在 GitHub API 有配额时运行 `uv run --python 3.12 python -m scripts.benchmark_external_resume_corpus`，对外部 Apache-2.0 合成 PDF 的独立 GT 进行结构化解析比较。相同外部挑战集最初为 **136/276 = 49.28%**，双语标题修复后 **143/276 = 51.81%**，有日期的公司＋职位拆分后 **156/276 = 56.52%**，中英文章节及多栏联系信息修复后为 **163/276 = 59.06%**；本轮新增基于 PDF 坐标的**保守双视图补充**，仅在原姓名/学历为空且可追溯原文时辅助补齐，最新固定基准为 **167/276 = 60.51%**（原文提取始终 255/276）。直接整栏重排的候选方法退化到 152/276，已否决；**仍未达到 90%**。已定位主要瓶颈为复杂排版的语义分块、公司和职位关系识别。

**工作职位的几何辅助校对（人工确认）：** 当 PDF 已有起止年月和工作经历，却无法拆出职位时，系统可依据同行的日期、机构和文字块提供**未经核实的候选关系**，在第二步显示原文、候选机构/职位、PDF 页码和三个文字块的定位坐标，并提供「已核对采纳 / 忽略」按钮。候选采用固定 schema，`confidence.tier=low`、`confidence.calibrated=false`，明确表示**尚无统计校准，不是任职概率**。**不点击采纳则不写入简历，也不影响评分或任职年限**。外部固定挑战集实测仅产生 1 条候选且与独立配对标注不一致，故严格禁止自动采纳；基础解析命中仍为 167/276（60.51%），不是新增识别增益。工程反例见 `tests/test_work_relation_geometry.py`、审计见 `scripts/profile_work_relation_gates.py`。

**PDF 关系监督实验（不影响正式功能）：** 使用独立开源合成 PDF 标注验证了“原文文字行定位 → 公司/职位关系数据 → CPU 小模型”接口。开发候选池为编号 21–40，固定挑战集为 1–10、101–105、201–205。纯几何基线与小型线性排序器在有独立 GT 唯一锚点的前提下得到相同结果（固定挑战集 29/29 个非平凡 Top-1），**训练未带来收益、模型未部署**，也完全不代表端到端简历识别准确率；完整实验及限制见 `docs/RELATION_SUPERVISION_20261019.md`。下一步应使系统不依赖 GT 自动寻找职位/公司候选，而不是继续训练容易的坐标排序任务。

**GT-blind PDF 字段候选试验（未部署）：** 在不向候选器输入任何 GT 的条件下，对独立开源样本定位可能包含公司/职位的原生文字行。开发池职位 GT 覆盖 34/45、公司 36/46；相同冻结配置在独立挑战集下降为职位 **27/50**、公司 **29/49**，因此该简单词面方法**未通过可泛化验收，不接入生产**，保留现有人工校对。详见 `docs/NATIVE_FIELD_CANDIDATES_20261019.md`。

**下一代 PDF 抽取研究（实验层、未部署）：** 使用独立 GT 唯一文字行训练过 CPU 行级分类器，扩大训练来源后仍未达到开发集旧词表覆盖与候选量门禁，因此**没有读取新冻结测试集，也没有推广模型**。进一步发现公司与职位常在同一文字行的不同字符区间，改用字符区间标注后，在 15 份训练 PDF 内恢复了原接口丢弃的 20 个正向监督锚点。该数字不是解析准确率；详细方法、失败记录与后续路径见 `docs/LINE_FIELD_SPAN_SUPERVISION_20261019.md`。

**GT-blind 字符片段提议器（实验失败，不部署）：** 使用 21–35 号公开合成 PDF 的独立 GT 正向字符区间学习职位/公司片段结尾与边界。在固定开发验证 36–40 的 5 份 PDF 上，职位完整字段命中 **4/13**、公司 **9/14**，人工候选 18 条；原词表方案的整行 GT 包含率分别是 10/13、10/14（33 条待核对），两种测量口径不同，且新模型未通过预设门禁。冻结测试 41–60 未读取，未接入产品。实验、等口径对照与失败边界见 `docs/GT_BLIND_SPAN_PROPOSER_20261019.md`。

**部分标注 BIO 监督接口（实验层，未训练）：** 从独立 GT 的 62 个职位/公司/学校正向片段出发，使用**唯一逐字定位、格式合法且不与目标冲突**的邮箱、电话、姓名和任职年月补充局部背景 `O`；仅年份、“至今”、重复和含糊的文本会弃权。训练编号 21–35 的 15 份公开合成 PDF 共 9,706 字符：477 个正向标签、535 个已核实 `O`（比联系信息单独标注多 189 个）、8,694 个 UNKNOWN；监督覆盖 **10.43%**。完整 BIO/CRF 训练条件仍不满足，产品解析基准未变。详见 `docs/PARTIAL_BIO_SUPERVISION_20261019.md`。

**部分标签损失与退化解（实验层，未训练）：** 合法 BIO 路径的精确条件边际似然不会把 UNKNOWN 当成 O。新增可信姓名/年月背景后复测：全 O 错 477 个已知标签、全职位错 **988** 个；但两种在 **8,694** 个 UNKNOWN 字符上给出相反预测的记忆策略仍都能取得近零损失。监督增强不等于未知区域可辨识，模型推广门禁继续关闭。详见 `docs/PARTIAL_BIO_OBJECTIVE_20261019.md`。

**WorkBlock PDF 版式区域实验（未部署）：** PyMuPDF 原生坐标 WorkBlock 在开发池 21–35 的 15 份 PDF 上实现公司/职位同块共现 **17/32**，旧 Entry 原文同段为 **19/32**，两路有互补但不自动合并（见 `docs/WORKBLOCK_REGION_DEV_20261019.md`）。随后在不修改项目依赖的隔离环境中实测成熟版式解析器 **PyMuPDF4LLM 1.28.2**：其 JSON→WorkBlock 当前适配仅 **9/32**，低于原有方法，因此**不部署**。已记录 PyPI 2.0 空兼容包、双许可证限制和完整对照，见 `docs/LAYOUT_ENGINE_ISOLATED_20261019.md`。

**成熟版式解析器损失归因（未部署）：** PyMuPDF4LLM JSON 中仍存在 29/32 组 GT 公司/职位文本，但旧适配器同块仅 9/32。实验性保留未知排版标题后恢复到 17/32，却与原生 PyMuPDF 的 17/32 完全重合，**无独有关系覆盖增益**，还新增 11 个缺少当前 GT 配对支持的候选区域，因此不推广。详见 `docs/LAYOUT_ENGINE_ISOLATED_20261019.md`。

规则权重和高/中/低阈值仍属**初版假设**。已完成 48 个合成层级情景、±20% 权重扰动测试，以及 1,680 组独立反事实关系的压力测试（`uv run --python 3.12 python -m scripts.stress_test_scoring`），据此修复了重复证据刷分和技能词表遗漏。但尚缺独立 HR 标注样本与真实筛选结果，**不能把分数写成录用概率或已验证的 HR 官方打分**。详情见 `docs/SCORING_METHODOLOGY.md` 和 `docs/R7_R10_CANDIDATE_DIAGNOSIS.md`。已提供完全离线的专家评分评价脚本：`uv run --python 3.12 python -m scripts.evaluate_hr_dataset --input evaluation_private/hr_labels.json`；私密数据集不会被 Git 跟踪。

## 经典简历编辑（/classic）

地址：**http://127.0.0.1:8766/classic**。

1. 拖拽上传一个 PDF、DOCX、DOC、PNG 或 JPG（最大 12 MB；PDF 最多 25 页）。
2. OCR 自动处理扫描图片和 PDF 内较大的图片文字。请核对识别提醒。
3. 在左侧修正姓名、联系信息、简介、技能、经历、项目与教育，右侧同步显示 A4 样式预览。
4. 选择本地安全整理；或者选择 AI 智能润色 → DeepSeek（默认）或自定义 API，并明确授权和提供该服务商的 Key。
5. 展开“查看原始识别文本”，对照原文核实数字、时间、公司、学校和措辞，勾选确认后导出 Word/PDF。

**重要边界：** 本地模式只清理排版/行文中的空白及列表符号，不包含大模型的语义重写；外部 AI 模式可以增强表达，但定性事实可能出错，必须逐项核实。数字变化、履历项数量变化和身份字段修改受到后端约束；此外，通过共用岗位规则表里明确的技术名词做逐字段新增检查，例如只有 Python 原文的工作描述不能被 AI 改成含 Kubernetes 的经历。**这只是已知技术名称的保守防线，无法验证工作真实性、职责归属、否定句和全部技术名词。**生成的结果始终属于可编辑草稿，AI 改动必须由用户逐条批准。

## 固定配置文件 settings.json

项目根目录的 **settings.json 是可提交 GitHub 的公共配置模板**。其中 `deepseek.api_key` 和 `configured.api_key` 最终都保留为空字符串 `""`；旁边的 `_api_key_comment` 说明了用途。标准 JSON 不支持 `//` 注释，所以使用 `_comment` 字段。

要在**本机长期保存 DeepSeek Key**，推荐新建根目录的 **settings.local.json**（已加入 `.gitignore`，不会提交 GitHub），内容只需要：

    {
      "deepseek": { "api_key": "粘贴你自己新生成的密钥" }
    }

如果不想在磁盘持久保存密钥，仍可以在网页右上角「AI 设置」中填写，刷新页面后失效。DeepSeek 永远使用官方 https://api.deepseek.com/v1 和模型 deepseek-flash，避免误把密钥发往其他服务。网页选择「AI 智能润色 → DeepSeek」，勾选发送授权后即可调用。**不要把真实密钥写入公开仓库、截图或聊天消息。**

**配置优先级**：当前页面输入 > `settings.local.json` > 旧环境变量 > `settings.json`。服务每次请求重新读取 JSON，修改本地配置一般不需要重启；刷新网页可以更新「已配置密钥」提示。

如果需要用环境变量临时配置 DeepSeek，仍支持 `PAPERPRO_DEEPSEEK_API_KEY`。


**自定义 OpenAI 兼容 API：** 在网页选择「自定义 API」，在 PowerShell 中设置会话级环境变量并启动服务：

    $env:PAPERPRO_OPENAI_API_KEY = "你的密钥"
    $env:PAPERPRO_OPENAI_MODEL = "gpt-4.1-mini"
    $env:PAPERPRO_OPENAI_BASE_URL = "https://api.openai.com/v1"
    uv run --python 3.12 python -m uvicorn app.main:app --host 127.0.0.1 --port 8766

自定义服务也可在 `settings.local.json` 的 `configured` 区域配置 `api_key`、`base_url` 和 `model`。网页输入的密钥只存在当前页面内存里，不写入磁盘。只有主动点击 AI 润色并勾选同意才会发送简历文字；未提供对应服务商的密钥时会明确报错。外部服务的数据处理政策以对应服务商为准。

## 隐私与局限

V3 求职者流程经明确授权后，将原件、草稿版本、报告、修改事件及导出记录保存在本机 `%LOCALAPPDATA%/PaperPro/candidate/candidate-tasks.sqlite3`，可通过 `PAPERPRO_DATA_DIR` 指定隔离目录。原件只读，数据不放公开静态目录，不默认用于模型训练。匿名任务归属由当前浏览器的 HttpOnly cookie 维持；清除 cookie 或更换浏览器后无法继续访问原任务。删除入口会删除该任务、原件及其历史，服务端随后拒绝访问和导出。已下载到用户电脑的文件需要自行删除。当前部署使用单进程 Uvicorn；重启后中断的处理会显示失败，可保留输入后重试。

网页输入的 API Key 和每次 AI 授权不写入任务数据库。如果你主动在本机 `settings.local.json` 中填入密钥，它会作为私人文件长期保存在磁盘中；该文件不会上传 GitHub。经典编辑器仍在请求中处理上传，未导出的编辑草稿不会因 V3 而自动保存。Word 转换仅使用操作系统临时目录并在正常结束时清理。V3 报告 PDF 使用独立中文布局；无法可靠呈现的罕见非 BMP 字符会提示改用 TXT，避免静默丢字。不要上传没有权限处理的第三方私人资料。

某些复杂表格、图片中的低分辨率文字、混排页面或罕见字体可能需要手动修正；原始识别文本始终可展开核对。PDF/PPT 风格的多栏简历可能无法自动恢复原布局：本项目的目标是统一生成固定模板，而非逐像素复刻原件。Watchdog 用于监督本次开发对话，不是简历网页的后台服务。
